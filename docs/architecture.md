# ArtFlowWeb Architecture

## 1. Назначение

ArtFlowWeb — публичный продающий сайт ArtFlow. Его задача не просто показать информацию, а провести пользователя по понятному пути:

```text
Увидел конкурс
→ понял пользу и условия
→ убедился в надёжности организатора
→ выбрал подходящий конкурс
→ снял сомнения через FAQ и доказательства
→ перешёл в Telegram
→ подал заявку в ArtFlowBot
```

Сайт не заменяет Telegram-бот. В MVP сайт отвечает за привлечение, доверие и выбор конкурса, а бот — за регистрацию и дальнейшую работу с заявкой.

## 2. Утверждённые архитектурные решения

| Решение | Выбранный вариант | Причина |
|---|---|---|
| Репозитории | ArtFlowBot и ArtFlowWeb раздельно | Разные задачи, релизы и структура кода |
| База данных | Одна общая PostgreSQL | Конкурсы и FAQ не нужно дублировать и синхронизировать |
| Frontend | HTML, CSS, Vanilla JavaScript, Jinja2 | Достаточно для информационного сайта, проще React |
| Backend | FastAPI | Python, понятные маршруты, возможность добавить API позднее |
| Доступ сайта к БД | Только чтение публичных таблиц | Ограничение ущерба при ошибке или уязвимости сайта |
| Связь с ботом | Telegram deep links | Пользователь сразу открывает выбранный конкурс |
| Адаптивность | Один responsive mobile-first сайт | Один URL и одна кодовая база для всех устройств |
| Размещение | Отдельный Railway-сервис | Обновление сайта не должно перезапускать бота |
| Дизайн | Реализует Codex по архитектуре и ТЗ | Владелец проекта контролирует структуру и проверку |

## 4. Ответственность приложений

### ArtFlowWeb

- отображает опубликованные конкурсы;
- показывает подробную информацию;
- отображает FAQ;
- показывает реальные доказательства доверия;
- формирует Telegram-ссылку на выбранный конкурс;
- адаптируется под телефон, планшет и компьютер;
- не создаёт и не изменяет заявки;
- не управляет администраторами;
- не скачивает музыкальные файлы участников.

### ArtFlowBot

- регистрирует Telegram-пользователей;
- принимает многошаговые заявки;
- сохраняет заявки и участников;
- управляет статусами;
- управляет конкурсами и FAQ;
- предоставляет админ-панель;
- принимает и выдаёт музыкальные файлы;
- обрабатывает параметр конкурса из deep link после отдельного изменения.

### PostgreSQL

- является единственным источником данных о конкурсах и FAQ;
- не дублируется для сайта;
- изменяется только через утверждённые миграции и административные сценарии.

## 5. Слои ArtFlowWeb

```text
HTTP-запрос
    ↓
Routes
    ↓
Services
    ↓
Repositories
    ↓
PostgreSQL
```

Каждый экземпляр FastAPI создаёт собственный `AsyncConnectionPool` в lifespan и сохраняет его в `app.state.database_pool`. Route передаёт pool через service в repository явно; repository не импортирует глобальное изменяемое состояние. `/health/db` использует pool того же приложения, а при завершении lifespan этот конкретный pool закрывается.

TTL-cache также принадлежит экземпляру FastAPI и хранится в `app.state.caches`. Для списков конкурсов, отдельных конкурсов, FAQ и `/health/db` используются отдельные ограниченные кеши. `asyncio.Lock` защищает только короткие операции с состоянием, а per-key in-flight future объединяет одинаковые cache miss: разные ключи загружаются параллельно, и исключения loader не кешируются.

### Routes

Отвечают за URL, параметры запроса, HTTP-статусы и выбор HTML-шаблона.

Примеры:

- `/`;
- `/competitions`;
- `/competitions/{competition_id}`;
- `/faq`;
- `/about`;
- `/contacts`;
- `/privacy`.

### Services

Содержат правила сайта:

- что считать актуальным конкурсом;
- какие конкурсы показывать посетителю;
- как определить статус регистрации;
- как сортировать конкурсы;
- как сформировать Telegram deep link;
- что показывать при закрытой регистрации;
- как очистить и подготовить FAQ для безопасного вывода.

Бизнес-дата определяется через `APP_TIMEZONE` и `zoneinfo`. Service сравнивает PostgreSQL `DATE` с текущей датой этой зоны; серверная `date.today()` для дедлайна не используется.

### Repositories

Содержат только работу с PostgreSQL:

- получение опубликованных конкурсов;
- получение одного конкурса;
- получение FAQ.

### Templates

Отвечают только за HTML-представление данных.

### Static

Содержит CSS, JavaScript, иконки и локальные публичные изображения сайта. CSS
подключается в фиксированном порядке: `base.css`, `components.css`, `pages.css`,
`responsive.css`. Это сохраняет единый cascade без препроцессора и inline-стилей.

### Observability

ASGI middleware создаёт request ID, добавляет `X-Request-ID` в ответ и логирует route template, status code и duration. Development использует читаемые строки, production — JSON. Query string, тело запроса и текст исключения в application log не включаются; для исключения сохраняются только тип и стек без значения ошибки.

## 6. Продающая логика

Страница должна последовательно отвечать на вопросы пользователя:

1. **Что это?** — понятный заголовок и предложение.
2. **Подходит ли мне?** — возраст, направления, город, дата и формат.
3. **Что я получу?** — сцена, опыт, дипломы, награды и другие подтверждённые результаты.
4. **Можно ли доверять?** — реальные фото, организатор, опыт, отзывы, контакты и положение.
5. **Сколько это стоит и что входит?** — прозрачная стоимость без скрытых условий.
6. **Как участвовать?** — короткая последовательность действий.
7. **Что делать дальше?** — одна заметная кнопка перехода в Telegram.

Запрещено использовать выдуманные отзывы, цифры, фальшивый дефицит или таймеры.

## 7. Telegram-интеграция

ArtFlowWeb формирует URL:

```text
https://t.me/BOT_USERNAME?start=competition_7
```

Ожидаемое поведение бота после отдельной реализации обработчика:

```text
/start без параметра
→ обычное главное меню

/start competition_7
→ проверка формата
→ проверка конкурса в PostgreSQL
→ сохранение selected_competition
→ карточка выбранного конкурса
→ кнопка подачи заявки
```

ArtFlowWeb не обрабатывает Telegram-параметр и не утверждает, что заявка уже открывается автоматически. Сайт только формирует ссылку. Разбор `competition_<id>`, проверка конкурса и выбор заявки должны быть реализованы отдельно в ArtFlowBot.

## 8. Размещение

```text
Railway Project: ArtFlow
├── Service: ArtFlowBot
├── Service: ArtFlowWeb
└── PostgreSQL
```

Сервисы используют одну базу, но разные команды запуска и разные переменные окружения.

## 9. Безопасность

- для сайта создаётся отдельная PostgreSQL-роль;
- роль сайта получает `SELECT` только на публичные таблицы;
- `.env` исключён из Git;
- SQL выполняется только с параметрами;
- ожидание соединения из пула ограничено коротким timeout;
- данные из БД экранируются перед выводом в HTML;
- трассировки и параметры подключения не показываются посетителю;
- сайт не получает доступ к `ArtFlow_bid`, `participants`, `users`, `admins`;
- deep-link параметр всегда проверяется на сервере бота.

## 10. Владение схемой базы

Пока владельцем схемы остаётся ArtFlowBot, потому что именно он создаёт таблицы в `database.py` и изменяет данные через админ-панель.

Правило:

- миграции общей БД хранятся в одном выбранном месте;
- ArtFlowWeb хранит документ `database_contract.md`;
- сайт не выполняет скрытые `ALTER TABLE` при запуске;
- существующие поля не удаляются и не переименовываются без отдельного плана совместимости.

## 11. Текущее состояние интеграции

- миграция публичных полей `competitions` выполнена;
- ArtFlowWeb читает только записи с `is_published = TRUE`;
- ближайшие конкурсы сортируются по `event_date ASC NULLS LAST`, затем по `id ASC`;
- `event_date`, `application_deadline`, `city`, `short_description`, `poster_url`, `rules_url` и `updated_at` доступны сайту;
- `directions` хранится как `TEXT` и преобразуется service-слоем в список;
- данные конкурса отображаются строго из соответствующих полей без смысловых подстановок;
- локальный путь `document` сайтом не читается;
- FAQ читается из таблицы `faq`, сортируется по `id` и выводится через service-слой;
- Telegram deep link формируется сайтом, но его обработчик остаётся отдельной задачей ArtFlowBot.
